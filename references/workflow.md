# 共用工作流规则

本 Skill 的需求整理、任务拆解和变更流程共用本文件。分类、记录例外和版本定位只在此维护；不要在各入口另写相反规则。

## 范围与分类

沿用用户已明确的授权范围。仅分析或讨论建议时不创建需求或 TODO；仅整理、拆任务时在对应阶段停止；已要求实现时继续实现和验证，不在阶段切换时重新请求批准。AI 建议不自动成为正式需求或任务。

- 需求变化：改变业务行为、数据、接口约定、验收标准或功能范围，包括新增、修改和移除功能。
- 缺陷修复：将已经约定的行为实现正确，没有改变业务规则或验收标准。先核对有效需求或协议，不因代码当前如此就认定它正确。
- 纯样式：只改变呈现，例如颜色、字号、间距和布局微调。若同时影响交互结果、信息结构或可操作性，相关部分按需求变化处理。
- mock：仅影响本地模拟面板、桥接、场景、回包或其错误路径的工作。不能仅凭文件名判定；影响真实产品行为的部分仍按需求变化处理。

## 文档记录与明确例外

需求变化应同步共享需求；是否建立持久任务、任务载体及多人拆分遵守 [任务规划规则](planning.md)，不要求每次生成 TODO。缺陷、纯样式和 mock 默认跳过两份文档，但已授权的实现仍执行共用交付标准。

**用户明确要求记录时，覆盖上述默认排除规则：**

- 只要求写需求：仅整理进需求，不自动新增 TODO。
- 只要求拆任务或写 TODO：可以只写 TODO，不为满足来源格式补建需求章节。来源写为「用户当次要求：具体问题或目标」，有明确问题编号、链接或材料位置时一并标注。
- 明确要求同时记录两份文档：先更新需求，再将 TODO 来源指向对应章节。
- 用户明确要求记录样式细节时，允许写入指定文档，后续合并、核对和交付均保留这一例外。
- 记录文档不等于授权实现；实现与记录范围分别遵守用户要求。

混合请求按工作项分类，只记录应记录的部分。跳过记录不重置已有任务；明确要求记录且旧任务确实需要重做时，允许更新该任务并恢复未完成。文档只反映当前有效要求，替换过时内容，重复输入不重复追加。

## 当前版本与路径

优先复用团队指定的有效需求来源及任务体系，不强制迁移到下列目录。以下是没有现有约定时的本地文档默认值；仅在需要创建文档时定位版本。任务平台记录不依赖本地版本目录。

- 用户明确指定版本优先；否则选择项目 `docs/` 下最大的数字版本目录。按点分数字比较，例如 v1.10 大于 v1.9；不按字符串排序。非数字或预发布名称存在歧义时不自行猜测。
- 没有可用版本目录且用户未指定版本时，询问目标版本；继续不依赖文档路径的已授权工作，不擅自创建 v1.0。
- 用户明确开始新版本时创建其指定版本；未指定新版本号时询问，不自行推定递增方式。
- 默认文档为 `docs/<版本>/需求.md` 和 `docs/<版本>/TODO.md`。用户明确指定其他输出路径时遵从并在后续阶段传递实际路径；输入素材路径不自动成为输出路径。
- 每个版本维护一份共享需求基线；单人使用一份 TODO，多人按规划规则使用工作包索引与分包任务，不按每次变更另建清单。按需创建以下结构，原始子目录已创建且为空时保留 `.gitkeep`；仅整理需求不提前创建 TODO 或 tasks/：

```text
docs/vX.Y/
  原始资料/
    前端方案/
    原始需求/
    server文档/
  需求.md
  TODO.md             # 需要本地任务时创建，单人清单或多人索引
  tasks/              # 仅多人本地协作时创建
    <工作包ID>.md
```

用户交来的原始材料按内容复制到对应子目录，C++ / 宿主和服务端材料统一归入 `server文档/`；不移动或覆盖原件，不把整理结果冒充原始材料。仅整理需求时不提前生成 TODO 内容。
