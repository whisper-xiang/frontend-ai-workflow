# 任务规划与多人协作

拆解或实现前读取本文件，先判断是否需要持久任务，再选择承载位置。这里只规定协作与核对方法，不自动创建子代理、分配人员、通知他人或写入外部任务平台；沿用用户授权及工具权限。

## 1. TODO 的生成门槛

| 情况 | 动作 |
| --- | --- |
| 用户明确要求任务清单 | 按指定载体拆解，到授权阶段停止 |
| 单点修复、简单样式调整、一步可验证的功能 | 直接实现与验证，不为流程强建持久 TODO |
| 多个可独立验收的结果、跨模块依赖、需要跨会话追踪 | 维护持久任务；不机械按文件数决定 |
| 多人协作、跨团队依赖或分阶段交付 | 明确工作包、依赖契约和集成责任，复用或建立持久任务 |
| 已有任务平台或清单足以承接当前工作 | 核对并复用，不再建立平行 TODO |

缺陷、样式与 mock 默认不建文档；涉及多人或外部依赖时也须明确边界，可先在回复或已有任务中说明，只有用户明确要求记录才创建对应文档。多项普通操作不等于多项可独立交付结果。不建 TODO 不降低验收或交付要求。

## 2. 选择唯一任务来源

- 优先沿用用户指定的载体及项目现有任务体系。已用任务平台时复用其编号、归属、依赖与验收字段，不同步维护另一份复选清单。
- 平台不可访问时说明未核实范围；可在回复中提供候选拆解，不声称已创建、同步或更新任务。不擅自另建一份持久清单作为替代。
- 单人且无现有体系时，默认使用当前版本的 TODO.md。
- 多人且无任务平台时，在当前版本的 TODO.md 中维护工作包索引及整体验收；详细任务放在 `tasks/<工作包ID>.md`。索引只写链接、归属、依赖与集成条件，不复制详细复选任务。已有等效结构直接复用。
- 每条任务只有一个权威状态位置；不将同一任务复制到总表与个人清单反复同步。平台与文档之间允许引用，不重复维护状态。

## 3. 按结果拆分工作包

先读取共享需求基线及相关协议，识别可独立交付结果，再拆任务。需求基线可以是项目唯一需求文档或团队指定的有效需求来源，不能让每人生成一套不同解释。

- 工作包写明目标、范围及不包含的相邻工作、需求来源、负责人、依赖和可验证完成条件。不按文件名机械拆包，不让两个包重复实现同一共享能力。
- 负责人及集成验收责任由用户或已有项目分工确定；未指定写“待指定”，不猜人名。归属缺失不阻止分析或独立且已授权的工作，但不得声称分工已确定。
- 共享组件、协议、公共类型和接口封装明确唯一负责包；调用方引用对应契约。存在同文件或公共 API 重叠时，标出修改边界，建议先落地公共变更或按顺序集成。
- 人员按已确认的工作包边界实施。开始与提交前核对共享需求和契约是否已变化，团队已有版本号、提交或文档链接时沿用以标明所依据的基线，不新建版本台账。共享需求的行为、接口和验收变化由团队指定维护者协调；未获共享修改授权时提出具体修改建议，不擅自覆盖其他人的有效要求。不是每次改动都增加审批。

## 4. 先定义依赖契约，再并行

跨包依赖至少明确：提供方、消费方、输入输出与错误语义、交付物位置、兼容约束、可用条件和验证方式。只填本次相关字段，已有协议直接引用，不另造一份协议。

- 区分已核实能力、已确认但尚未实现的目标，以及未决约定。文件存在不能证明接口可用；未核实假设不写成事实。
- 契约明确且模拟不会掩盖关键差异时，可先独立开发消费方。本地模拟只证明本地逻辑，不能勾选真实联调任务。
- 契约未决且影响行为或验收时，询问具体问题，不以猜测实现；可继续不依赖该决定的工作。
- 检查循环依赖：可先独立定义共享契约，或合并不能独立验收的包；不能只调整列表顺序掩盖循环。
- 契约变化时核对消费方、受影响需求和任务；保留不受影响的已完成状态，不批量重置。

## 5. 实现完成与集成完成分开

一个包可以完成本地实现，但总体交付仍可能等待其他包。将本地可验证工作与必需真实联调分成独立任务；已欠集成的包不能宣称端到端完成。

跨包用户主路径必须有集成任务、完成条件及明确责任人；责任未确定时标出缺口。集成条件来自已有需求，包含实际调用与受影响的主路径，不只写“联调通过”。不把其他人的状态当作已验证事实。

## 6. 三次核对任务准确性

任务生成后回读，按顺序核对。小任务可直接在回复中简述结论，不另建核对报告。

1. **需求覆盖**：每项明确需求及验收有任务承接，或有依据表明已满足而无需修改；每条新增任务有来源。重复、无来源建议及未决方案不能作为正式实施任务。
2. **实现可行性**：核实相关代码、复用能力、协议与调用方；区分实际存在和待实施目标。完成条件与实际验证方式匹配，未核实假设明确标注。
3. **协作可交付性**：核对包边界、归属、重复工作、依赖、循环与集成责任。拆开“本地完成+等待外部”混合任务，确认每条能独立判断完成。

每条任务应能回答：为什么做、完成后可观察到什么、依赖什么、如何确认完成。复杂或高依赖分工在回复中列出需要负责人确认的具体边界，不要求所有任务新增审批。

## 7. 稳定标识与状态

- 复用现有平台或项目稳定 ID。没有约定的多人文档可用 `WP-QUERY`（包）、`WP-QUERY-01`（任务）等可读 ID；检查目标文件和索引避免冲突，不擅自改现有 ID。
- ID 创建后不随排序变化、不复用已删除任务 ID。新增任务取未使用 ID，移除任务需要保留依赖线索时写成非复选说明并更新引用。
- 单人 TODO 仍可用连续序号；跨包依赖不引用会变化的序号。多人任务如展示序号，只在各文件内连续排列，不要求全文跨文件重排。
- 仅更新本次负责且授权的任务状态；合并他人任务变更时保留有效内容，有冲突先核对，不覆盖或假定他人已完成。

## 示例：查询与导出

共享需求明确查询行为、筛选条件及导出规则后，可拆：公共查询契约、查询页面、导出功能、集成验收。页面与导出依赖同一筛选契约；契约确认后可并行。本地 mock 验证与“真实查询条件正确传入导出并得到符合需求的结果”分开验收。负责人由团队指定，不能把该示例的业务行为自动套入其他需求。
