# req-todo：检索并罗列任务

维护与需求对应的一份 TODO，明确工作内容、完成条件和改动范围，不增加审批、复杂状态或检索报告。

## 1. 确认输入与范围

- 读取当前请求、对应需求和已有 TODO，沿用已明确的授权范围。仅调用本 skill 时默认做到 TODO；要求实现时继续编码。
- 优先使用指定或当前对话已确定的文档路径，否则按项目约定查找并核实内容。多个合理候选无法确定时询问目标，不任选或覆盖。
- 需求缺失或落后于最新要求时，先读取同级的 [req-init](../req-init/SKILL.md)，仅执行其需求整理阶段，完成后返回本步骤；不要让它再次进入 req-todo。若该 skill 不可用，按项目规则合并最新要求并说明，不声称已调用它。
- 输入不可读、没有可执行要求或存在影响业务、验收、范围的未决问题时，说明缺口，不凭空拆任务；继续不受影响且已授权的部分，不推进依赖未决问题的实现。
- TODO 路径优先沿用已有对应文件或项目约定；无约定时使用 `docs/todo/<与需求相同的文件名>.md`。写入前核实文件用途。

## 2. 按规模检索

依次读取：

1. 目标目录适用的项目规则、配置与必要的 README，确定实际 lint、类型检查命令和现有验证方式。
2. 目标模块的类似实现、共享组件、hooks/composables、请求封装、状态与样式约定。
3. 拟复用接口和调用示例；修改公共接口时检查实际受影响的调用方。

文案修改只需相关文件与规则；页面功能查看相关公共能力；公共接口变更才扩大到调用方。找到适用规则、主要参考、拟复用接口和验证方式即可停止。找不到时简述已查范围与缺口，采用范围内最小实现，不无限扩大检索。

显式规则和配置优先，历史代码只是参考。不能仅凭文件名认定可复用，不虚构路径或符号。普通技术选择按项目约定处理；只有方案额外改变业务行为、验收或范围且尚无明确决定时才询问。

## 3. 创建或更新 TODO

新建时读取 [TODO 模板](templates/todo.md)；已有文件保留有效结构和无关人工内容。

- 每条写清做什么、如何判断完成、涉及哪里。共享范围和实现参考放在列表开头，局部例外写在对应条目下；简单任务可省略实现参考。
- 用排列顺序表达必要依赖，将任务拆到可以独立判断完成的粒度，不为每个文件或机械步骤建立条目。
- 仅使用 `- [ ]` 和 `- [x]`。新增工作保持未勾选；保留仍适用的已完成状态，不能因刚生成清单或看到了相关文件就勾选。
- 已完成条目需要重新实现时，更新内容并恢复 `- [ ]`。重复输入只修改现有内容，不重复追加任务。
- 不再需要的条目删除或写成普通删除线文本，例如 `~~旧的导出任务~~`，不保留为待完成复选框。若需移除入口或清理代码，另列普通未开始任务，并核实共享代码是否仍被使用。
- 覆盖本次需求及其验收，不将优化建议变成任务，不增加任务编号、状态表、依赖矩阵或证据台账。

保存后读取结果，对照需求检查覆盖、范围、完成条件、重复条目及原有完成状态。TODO 已保存且必要检索完成，即结束拆解阶段；这不代表实现已完成。

## 4. 后续动作

- 仅拆任务：回复 TODO 路径、主要任务和必要缺口后停止，不编码。
- 已要求实现：直接执行本次授权范围内的 TODO，不因清单生成再次请求批准，不自动执行其他任务。
- 由 req-change 调用：将需求路径、TODO 路径、本次范围及必要问题交回调用流程，由它继续；不调用 req-change，也不启动第二轮实现。
- 执行范围确实不明时，先完成明确授权的拆解，再针对是否实现询问。

## 5. 编码与完成规则

本节仅在已经授权实现时执行，也是 req-change 的共用完成规则。

- 按任务顺序及已核实的项目规范实现，复用已有能力，不顺手重构无关代码。文档不再符合最新要求时先同步文档，再继续依赖它的实现。
- 根据需求与项目已有验证方式检查相关行为，运行项目已有的 lint、类型检查；无需为每条任务额外增加测试、截图或人工复核关口。
- 功能满足 TODO 和验收要求，且已有检查已运行后勾选。缺少对应检查命令时，只要功能满足就立即勾选，并说明未执行哪些检查；仍执行其他已有的检查，不另建检查体系。
- 报错如实说明，不把运行过写成通过。报错反映任务要求未满足时先修复；无关既有问题说明即可，不扩展范围。已有命令因环境无法执行时说明原因，不将其当作缺少命令而默认完成。
- 未满足完成条件的条目保持未勾选；逐项处理结果，不因部分任务完成而勾选整份清单。回复实现变化、检查结果及必要未解决事项，不维护证据表。
