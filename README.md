# frontend-workflow

通用前端开发工作流 Skill。把「整理需求 → 拆任务 → 按项目现有技术栈实现 → 验证交付」收成一套可安装的说明，供 Cursor 等支持 Agent Skill 的工具在前端任务中自动遵循。

它不绑定 React、Vue 或某一种目录约定，也不要求先安装其他需求 Skill。进入具体项目后，从该项目的配置、代码和已有文档识别技术栈与任务体系，再按实际约束工作。

## 适合什么时候用

在前端项目里做下面这些事时启用本 Skill：

- 把口头需求、方案或接口说明整理成当前有效需求
- 把需求拆成可独立验收的任务，或拆成多人工作包
- 实现功能、处理需求变更
- 修复缺陷、调整样式、改本地 mock
- 核对交付范围、验证结果和未完成项

仅分析或讨论时，只读取材料并回复，不创建需求文档、TODO，也不改业务代码。

## 不做什么

- 不把本 Skill 的安装目录当成业务项目根目录
- 不强制迁移技术栈，不因缺少专项 Skill 而自动下载安装
- 不把 AI 建议自动写成正式需求或任务
- 不在未授权时实现代码，也不在阶段切换时重复索要批准
- 不新建审批流、变更台账或强制交付报告
- 不自行指定负责人、通知他人，或在任务平台不可达时假装已经同步

## 目录

```text
frontend-ai-workflow/
├── SKILL.md                      # 入口：五段流程与停止条件
├── references/
│   ├── workflow.md               # 请求分类、记录例外、版本与路径
│   ├── planning.md               # 任务门槛、工作包、依赖契约、三次核对
│   ├── development.md            # 技术栈发现与实现约束
│   └── delivery.md               # 按改动选择验证、勾选与回复要求
└── templates/
    ├── requirement.md            # 需求基线
    ├── todo.md                   # 单人清单或多人工作包索引
    └── work-package.md           # 单个工作包
```

`SKILL.md` 里的相对链接以技能目录为根。业务文件写到目标项目，或用户指定的工作区包，不写进技能目录。

## 安装

本目录是一份自包含 Skill，整体复制即可，不要只拷 `SKILL.md`。

| 范围 | 路径 | 效果 |
| --- | --- | --- |
| 个人 | `~/.cursor/skills/frontend-workflow/` | 本机所有项目可用 |
| 项目 | `<业务仓库>/.cursor/skills/frontend-workflow/` | 随该仓库共享给协作者 |

不要安装到 `~/.cursor/skills-cursor/`。那是 Cursor 内置技能目录。

其他支持 `SKILL.md` 的工具，安装到该工具自己的技能目录，目录名保持 `frontend-workflow`。技能名来自 frontmatter 的 `name` 字段。

安装后，在**业务项目**里提出前端需求、拆解或实现请求。代理会读取本 Skill，但文档和代码落在业务项目中。全局安装时，先确认当前目标项目，再读它的 `AGENTS.md`、README、`package.json` 和构建配置。

## 代理如何执行

入口在 [`SKILL.md`](SKILL.md)。已说明授权范围的对话，进入下一阶段时不再重复确认。

```text
确定范围
    │
    ├─ 仅分析或讨论 ──────────────► 回复后停止
    ├─ 仅整理需求 ──► 写需求 ─────► 停止
    ├─ 仅拆任务 ────► 必要时同步需求，写任务 ► 停止
    └─ 已授权实现
           │
           ├─ 判断要不要持久任务
           ├─ 识别项目技术栈与现有任务体系
           ├─ 只做本次范围
           └─ 按交付标准验证并说明结果
```

只说出 Skill 名称、没有具体要求时，先问目标，不自行生成需求或改代码。需求类请求若未明确说「实现」，默认整理需求并拆任务后停止。

## 请求怎么分类

分类规则只维护在 [`references/workflow.md`](references/workflow.md)。

| 类型 | 含义 | 默认是否写需求 / TODO |
| --- | --- | --- |
| 需求变化 | 改变业务行为、数据、接口约定、验收或功能范围 | 同步共享需求；任务是否持久化另看门槛 |
| 缺陷修复 | 把已约定行为做对，不改业务规则 | 跳过两份文档 |
| 纯样式 | 只改颜色、字号、间距、布局等呈现 | 跳过两份文档 |
| mock | 只影响本地模拟、桥接、场景或回包 | 跳过两份文档 |

样式如果同时改变交互结果、信息结构或可操作性，相关部分按需求变化处理。mock 不能只看文件名；影响到真实产品行为的部分仍按需求变化处理。

用户点名要记录时，按点名范围写，不连带补另一份文档：

- 只写需求：不自动补 TODO
- 只拆任务：可以不补需求章节，来源写「用户当次要求」
- 两份都要：先更新需求，TODO 来源指向对应章节

混合请求按工作项分开处理。跳过记录不会把已有任务清掉。

## 需求文档

优先复用团队已经指定的需求来源，不另抄一套。没有现有约定、并且这次确实要落本地文档时，才使用下面的默认布局。

版本选择：

1. 用户指定的版本优先
2. 否则用项目 `docs/` 下数字最大的版本目录（`v1.10` 大于 `v1.9`，按点分数字比较）
3. 没有可用版本时询问，不擅自创建 `v1.0`
4. 新版本号未说明时询问，不自行决定怎么递增

默认文件：

```text
docs/vX.Y/
  原始资料/
    前端方案/
    原始需求/
    server文档/          # C++、宿主、服务端材料都放这里
  需求.md                # 当前有效需求，一个版本一份
  TODO.md                # 需要本地任务时才创建
  tasks/                 # 仅多人、且没有任务平台时创建
    <工作包ID>.md
```

原始材料按内容复制进对应子目录，不移动、不覆盖用户手里的原件。整理结果不放进 `原始资料/`。只整理需求时，不提前创建 `TODO.md` 或 `tasks/`。

需求正文用 [`templates/requirement.md`](templates/requirement.md)：一个主题一节，写目标、功能要求和可观察的验收。新主题追加章节，不另建文件。冲突内容替换旧要求，重复输入不重复追加；不受影响的功能和验收保留。验收里不擅自补权限、排序、默认值或性能指标。删除功能时去掉失效需求和验收；仅整理阶段不删代码。

## 任务怎么拆

规则在 [`references/planning.md`](references/planning.md)。先判断要不要持久任务，再选唯一载体。

| 情况 | 做法 |
| --- | --- |
| 用户明确要任务清单 | 按指定载体拆，到授权阶段停止 |
| 单点修复、简单样式、一步能验证的功能 | 直接做和验证，不为流程建 TODO |
| 多个可独立验收的结果、跨模块依赖、需要跨会话追踪 | 维护持久任务 |
| 多人、跨团队或分阶段交付 | 写清工作包、依赖契约和集成责任 |
| 已有任务平台或清单够用 | 复用，不再建平行 TODO |

载体只留一个权威状态：

- 已有任务平台：沿用其编号、归属和验收，不另维护一份复选清单。平台打不开时，只在回复里给候选拆解，并说明未核实，不声称已同步。
- 单人、且没有现有体系：当前版本一份 [`TODO.md`](templates/todo.md)，序号连续。
- 多人、且没有任务平台：`TODO.md` 只做工作包索引；详细任务放在 `tasks/<工作包ID>.md`，模板见 [`templates/work-package.md`](templates/work-package.md)。索引不复制复选状态。

每条任务要能回答：为什么做、做完能看到什么、依赖什么、怎样确认完成。单人用连续序号；跨包引用用稳定 ID（如 `WP-QUERY`、`WP-QUERY-01`）。ID 不随排序改变，已删除的 ID 不复用。未指定负责人时写「待指定」。

跨包依赖至少写清提供方、消费方、输入输出与错误语义、交付物位置、兼容约束、可用条件和验证方式。本地 mock 通过不能勾选真实联调。用户主路径要有单独的集成任务和责任人；本地做完不等于端到端完成。

任务写完后按这个顺序回读：

1. 需求覆盖：明确需求有任务承接，或已满足故无需修改；每条新任务有来源
2. 实现可行性：相关代码、复用能力和调用方已核对；没核实的假设单独标出
3. 协作可交付性：包边界、归属、重复工作、循环依赖和集成责任说得清

## 实现约束

开发规则在 [`references/development.md`](references/development.md)。实现前先看目标项目，而不是套一套固定框架写法。

- 读适用的 `AGENTS.md`、项目规则和 README；没有这些文件也可以继续
- 用 `package.json`、锁文件、工作区和构建配置确认包管理器、框架版本和该在哪个目录跑命令
- 确认是 CSR、SSR/SSG、WebView、小程序还是其他运行形态
- 命令以现有 scripts、配置和 CI 为准，不按脚本名字猜测用途
- 复用已有组件、请求封装、状态和样式变量
- 协议以有效材料为准，不猜字段，不伪造成功，不绕过鉴权、错误处理和内容净化
- 只改本次范围；保留无关的未提交改动
- JavaScript 项目不强制改成 TypeScript，旧框架不顺手升级
- 构建、类型检查和业务测试分别确认，一种通过不代表另一种通过

## 交付

标准在 [`references/delivery.md`](references/delivery.md)。只改文档时做保存后回读，不跑业务构建。跳过需求或 TODO，仍然要验证代码改动。

按改动选择验证：页面和表单看主路径以及加载、空数据、失败、重复操作；样式看实际页面和受影响尺寸；接口和宿主桥接把本地模拟与真实联调分开写；公共组件核对调用方。使用项目里已经存在的 lint、类型检查、测试或构建命令。没有的命令不编造，也不为了过关新造一套检查。浏览器或宿主不可用时，写明哪一段行为没验证。

任务满足完成条件且适用检查通过后，立即勾选该条。环境原因没跑成的必要检查，不能当成「项目没有这条命令」而勾上。回复里说明实际变化、验证结果和剩余问题，并给出本次更新的文档路径或已有任务链接。

## 使用示例

下面的说法会落到不同阶段。示例都假设 Skill 已安装，并且当前打开的是业务项目。

整理需求，不写代码：

```text
根据这份接口说明，整理查询页和导出的需求。先不要实现。
```

只拆任务：

```text
按当前 v1.2 需求，把查询和导出拆成可并行的工作包。先不要写代码。
```

在已有需求上实现一个明确范围：

```text
实现需求里的筛选查询。导出不要动。
```

缺陷或样式，默认不建文档：

```text
筛选按钮和输入框重叠了，按现有布局规矩修好。
```

点名留下记录：

```text
这个空状态文案改成「暂无结果」，同时写进 v1.2 需求，不要建 TODO。
```

## 设计原则

- 一个版本一份共享需求，一种工作一个权威任务状态
- 文档记录的是当前有效要求，过时内容替换掉，而不是不断追加
- 代码现状不能覆盖已经明确的新要求；缺陷先对照需求和协议，不以「代码现在就是这样」当成正确行为
- 未决且影响验收的问题先问清楚；不依赖该决定的工作可以继续
- 多人协作只改本次授权的任务，不用别人的勾选代替自己的验证
