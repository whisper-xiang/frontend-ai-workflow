# req-init：整理需求

将最新要求合并到一份可供后续拆解和实现的完整需求文档。保留仍有效的内容，替换冲突的旧要求，不按每次变化新建版本或变更记录。

## 1. 确定范围与输入

- 沿用当前对话已明确的执行范围：仅整理需求、整理并拆任务、或继续实现。只调用本 skill 而没有要求后续工作时，完成需求整理即停止。
- 接受对话描述、用户提供的文本、Markdown、截图或指定素材路径。不要求先将输入放入 `docs/inbox/`。
- 读取适用的项目规则和与本次需求有关的素材；此阶段不为拆任务而扫描整个代码库。只有理解现有业务必需时才读取相关实现，代码现状不能覆盖开发者明确的新要求。
- 输入为空或不可读时，说明具体缺失，不凭空生成需求。部分输入可读时可整理已明确部分，但不得把未读内容当作已覆盖。

## 2. 定位需求文档

1. 优先使用开发者明确指定的需求文档；素材路径不自动等于输出路径。
2. 未指定时，沿用当前对话已确定的需求路径；否则按项目文档约定，在需求目录中查找对应业务主题，并读取候选内容核实。
3. 有唯一对应文档时原地更新；有多个合理候选且无法确定归属时，询问目标，不任选文件或重复新建。
4. 没有对应文档时，按项目约定新建；无约定则使用 `docs/requirements/<需求名称>.md`。名称简短、对应业务主题，不强制编号或日期。写入前确认同名文件用途，避免覆盖无关内容。

新建时读取本 skill 相对路径下的 [需求模板](templates/requirement.md)，填写目标、功能要求和验收标准。已有文档保留其有效结构与人工内容，不为套模板重写整篇。

## 3. 合并当前有效要求

- 以开发者最新明确描述为准，直接修改对应段落。新要求与旧描述冲突时替换旧描述，不将两个冲突版本并列保留。
- 保留未受影响的功能、约束和验收内容；重复处理相同输入时，不追加重复段落。
- 将验收标准写成可观察的行为，并且可追溯到明确要求。不要擅自补入排序、权限、分页、默认值、性能指标等业务决定。
- 开发者明确移除功能时，同步移除其功能要求及不再适用的验收描述；保留其他功能仍依赖的有效内容。仅整理阶段不删除代码或修改 TODO。
- AI 的建议只在回复中说明，不写成正式需求，也不自动变成任务。
- 只有缺失信息会影响业务行为、验收标准或任务边界时，针对具体问题询问。已经明确的调整直接更新，不重复确认；普通措辞和结构选择自行处理。
- 有未决业务问题时，可保存不受影响的已明确内容，并在回复中指出缺口；不把猜测写成结论，不宣称需求已完整，也不推进依赖该决定的工作。
- 不增加审批状态、审批版本、修订历史、CHG、决策台账或单独的交接文件。来源链接有实际追溯价值时再保留。

## 4. 核对与结束

保存后读取修改结果，核对：

- 本次明确要求均已体现，目标、功能要求和验收标准相互一致。
- 旧的冲突描述已替换，未受影响的有效内容未丢失。
- 没有将建议或推测写成业务要求，没有重复内容。

文档保存成功且影响后续工作的业务歧义已明确，才算本阶段完成。写入失败或存在未决问题时，如实说明具体阻碍，并继续不受影响的已授权部分。

## 5. 后续动作

| 当前授权范围 | 本阶段完成后 |
| --- | --- |
| 仅整理需求，或仅调用 req-init | 简述新增或更新内容，返回需求文档路径后停止；不更新 TODO、不编码 |
| 整理并拆任务 | 继续 req-todo，TODO 产出后停止 |
| 已要求实现 | 继续 req-todo，再进入当前对话的编码与检查阶段；不在 skill 切换时再次请求批准 |
| 由 req-todo 或 req-change 限定为需求整理阶段调用 | 将结果交回调用流程，由它按原有授权范围继续；不自行调用 req-todo 或 req-change，避免循环 |

交接仅携带需求路径、已有 TODO 路径（若已知）、本次授权范围和必要的未解决问题。若 req-todo 在目标环境中可用，读取并使用它；尚未安装时，说明缺少该 skill，并按项目已有任务拆解规则继续已授权工作，不声称已调用它，也不自行安装。项目也没有拆解规则时，按需求生成最小可验证 TODO 后继续已授权工作。

执行范围确实不明时，先完成明确授权的整理部分，再针对是否继续询问；不能仅因用户提供了需求描述就开始编码。
